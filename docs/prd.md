# Skill 整合与项目推荐平台产品需求规格说明书（PRD）

> 文档状态：需求基线 v1.0  
> 更新时间：2026-08-26  
> 产品名称：Skill 整合与项目推荐平台（暂名）  
> 首期目标平台：WorkBuddy、千问办公、豆包工作  
> 扩展来源：GitHub、Hugging Face、创作者公开提交及后续合规公开来源

---

## 1. 文档目的

本文档定义 Skill 整合与项目推荐平台的产品目标、范围、用户、核心流程、测试与评分规则、项目推荐逻辑、信息架构、数据对象、安全与合规边界、商业模式、分期计划和验收标准。

本文档是产品、设计、研发、测试、运营、法务和商务共同使用的需求基线。未经重新评审，不应把本文明确排除的企业私有 Skill、Skill 文件分发或未经证据支持的排行榜加入实施范围。

## 2. 已确认的核心决策

以下事项已经确认，不再作为开放问题重复讨论。

| 编号 | 已确认决策 | 说明 |
| --- | --- | --- |
| D-001 | 首期重点覆盖 WorkBuddy、千问办公、豆包工作 | 三个平台分别代表腾讯、阿里/钉钉、字节/飞书的办公 Agent 生态 |
| D-002 | 企业私有 Skill 完全排除 | 当前产品不获取、不测试、不展示，也不尝试绕过企业或组织权限；未来如企业主动授权，应另行立项，不自动纳入本 PRD |
| D-003 | 收录所有通过正常渠道能够发现的公开 Skill | 包括三家公开市场、GitHub、Hugging Face、创作者公开提交；只有元数据时仍可收录名称和来源 |
| D-004 | 平台不销售 Skill 文件 | 商业价值来自选型、测试证据、组合推荐和治理能力 |
| D-005 | 用户侧不提供 Skill 文件下载 | Skill 安装跳转到原始来源或原平台，不托管公开下载副本 |
| D-006 | 不做三家市场镜像 | 不复刻原市场页面、详情正文、脚本、附件或下载服务 |
| D-007 | 不用下载量、Star 或单次 LLM 打分冒充真实能力排名 | 热度只能作为辅助信号，不能作为任务效果结论 |
| D-008 | 所有能够取得 Artifact 的公开 Skill 进入完整静态检测 | 只有名称和来源的候选只做来源与元数据核验，并标记 `METADATA_ONLY`；未实测不生成动态分数 |
| D-009 | 动态测试采用分级准入 | 许可证、来源、安全、依赖和可运行性满足要求后才进入执行环境 |
| D-010 | 推荐单位是项目 Skill 组合 | 既推荐单个 Skill，也推荐带版本、依赖、权限、验收和回退的 Bundle |
| D-011 | Skill、连接器/MCP、专家/工作伙伴分开建模 | 三者可以组合，但不能混成一个数量或评分口径 |
| D-012 | 高风险操作由人确认 | 删除、支付、发送、发布、审批、生产写入等不得静默自动执行 |

## 3. 产品概述

### 3.1 一句话定义

收录所有可通过正常渠道取得的公开 Skill，通过全量静态检测和分级动态实测，为用户推荐适合其项目、平台、预算和安全要求的 Skill 及 Skill 组合。

### 3.2 产品定位

本产品不是 Skill 下载站，也不是某一家办公 Agent 的附属市场，而是独立的：

1. 公开 Skill 发现与去重索引；
2. Skill 静态质量与安全检查平台；
3. Skill 真实任务评测与跨平台兼容实验室；
4. 项目级 Skill 组合和个性化推荐引擎；
5. 企业内部 Skill 选型、批准、版本和使用治理工具。

### 3.3 核心价值

用户不需要逐个寻找、安装和试错大量 Skill。平台回答五个问题：

1. 市面上有哪些公开 Skill 能解决当前任务？
2. 哪些 Skill 真正完成过相同或近似任务？
3. 它在用户选定的平台、模型和操作系统上是否兼容？
4. 它需要哪些权限、账号、密钥、连接器和费用？
5. 一个项目应该安装哪些 Skill，哪些不应同时安装？

## 4. 背景与机会

### 4.1 市场变化

WorkBuddy、千问办公和豆包工作均在形成“Skill + 连接器/MCP + 专家或工作伙伴”的能力体系。与此同时，GitHub、Hugging Face 和各类开放社区已经出现大量 `SKILL.md`、脚本、工作流和 Agent 能力包。

供给快速增加后，用户面临的问题从“没有 Skill”变成：

- 不知道去哪里找；
- 名称和描述高度重复；
- 下载量不代表有效；
- 同名 Skill 的来源、版本和内容不同；
- 在一个 Agent 可用，在另一个 Agent 不一定可用；
- 依赖、密钥、外部服务和权限常被隐藏；
- Skill 可能降低结果质量或引入安全风险；
- 用户最终需要的是完成项目，而不是安装更多 Skill。

### 4.2 市场缺口

现有产品通常只覆盖以下部分能力：

- 原生市场擅长安装和平台内分发，但不做中立横向比较；
- 聚合目录擅长搜索和统计，但真实任务测试不足；
- 安全扫描平台擅长发现恶意代码，但不判断业务效果；
- 模板市场提供单个模板，但缺少项目级依赖和冲突分析。

本产品的切入点是“公开来源全量发现 + 证据化实测 + 项目组合推荐”。

### 4.3 竞品与替代方案分析

当前竞争不是单一同类产品之间的竞争，而是五类产品分别解决用户的一部分问题。

| 类型 | 代表 | 主要价值 | 主要优势 | 相对本产品的空白 | 本产品关系 |
| --- | --- | --- | --- | --- | --- |
| 办公 Agent 原生生态 | WorkBuddy、千问办公、豆包工作 | 在原平台发现、安装和使用 Skill | 原生体验、账号体系、平台能力调用 | 通常围绕单一生态，缺少跨平台中立评测和项目组合比较 | 首期核心数据来源、兼容目标和潜在合作方 |
| 公开代码与模型社区 | GitHub、Hugging Face | 托管、搜索和协作公开仓库 | 供给广、版本历史清楚、开发者密度高 | Skill 定义不统一，Star/下载量不能证明实际效果 | 主要增量发现来源，不替代原站托管 |
| Skill 聚合目录和导航站 | 各类 Skill 目录、榜单和搜索站 | 快速发现、分类和查看热度 | 上线快、SEO 和长尾覆盖强 | 常缺少版本化测试、失败证据、权限分析和组合建议 | 搜索入口层面的直接竞品 |
| Agent 评测与学术基准 | SkillsBench、GitSkills 等 | 提供任务集、数据集和研究方法 | 方法透明、可复现性较强 | 面向研究或数据集，不直接完成用户选型、安装跳转和项目配置 | 评测方法参考与潜在数据合作方 |
| 安全扫描与供应链工具 | SAST、依赖扫描、沙箱和恶意代码检测产品 | 识别代码、依赖和行为风险 | 安全规则和隔离能力成熟 | 不回答业务任务是否有效，也不生成项目级 Skill 组合 | 底层能力供应方或集成对象 |
| 顾问、实施商与内部 AI 团队 | 人工选型和项目交付 | 根据业务情境给出组合方案 | 对组织和业务理解深 | 成本高、难标准化、证据难复用 | 高客单价场景的替代方案及企业渠道伙伴 |

竞争判断：原生平台控制安装入口，代码社区控制开放供给，目录站控制搜索流量，评测项目控制方法话语权。本产品应占据“跨来源证据层 + 项目决策层”，避免与原平台争夺文件分发和安装控制权。

可建立的差异化壁垒包括：

1. 按版本、平台、模型和任务持续积累的可复现实测数据；
2. 同名和分叉 Skill 的跨来源谱系、哈希和版本关系；
3. 失败案例、权限、依赖、成本和兼容性组成的证据图谱；
4. 从单 Skill 排名升级为项目 Bundle 的依赖、冲突和验收能力；
5. 创作者申诉、复测和企业治理形成的长期反馈闭环。

### 4.4 可行性分析与结论

| 维度 | 可行性 | 判断 | 关键约束 | 验证方式 |
| --- | --- | --- | --- | --- |
| 公开来源发现 | 中高 | GitHub、Hugging Face 和公开页面足以启动供给库 | 三家原生市场未必提供稳定批量 API，页面和客户端结构可能变化 | 每个来源完成增量发现、版本识别和失效恢复 PoC |
| Artifact 获取与归一 | 中 | 可公开取得的仓库和本地安装内容可以建立统一档案 | 并非所有可见条目都允许复制、执行或公开测试结果 | 分开记录“可见、可取得、可测试、可公开结果”状态 |
| 全量静态检测 | 高 | 解析、依赖提取、规则扫描、许可证识别和哈希去重均可工程化 | 多种 Skill 格式、混合脚本和误报 | 以人工标注样本测量召回率、误报率和解析成功率 |
| 中立动态测试 | 中 | 文档、表格、演示、网页、研究等任务可在受控沙箱重复运行 | 模型波动、外部账号、付费 API、GUI 和操作系统差异 | 固定环境、基线对照、重复运行、确定性验收和成本上限 |
| 三家原生环境测试 | 中低 | 可通过独立设备、测试账号和 Worker 探索 | 安装协议、自动化稳定性、账号风控及结果公开权不确定 | V0 逐家 PoC；协议不成立时降级为兼容性说明或内部报告 |
| 跨平台比较 | 中 | 可用 Canonical Schema 和能力标签统一公共维度 | 同一名称不代表同一实现，宿主能力会影响结果 | Artifact 哈希、行为测试、宿主基线和证据等级共同约束结论 |
| 项目 Bundle 推荐 | 中高 | 规则、依赖图和模板足以先做可解释版本 | 冷启动反馈少，自动推荐容易过度承诺 | 首期规则优先、人工审核、三档方案和可替换项；再逐步学习排序 |
| 法务与合规 | 中 | 只展示必要元数据、结果和原始来源跳转可显著降低风险 | 许可证、平台协议、商标、抓取、测试和结果公开权需逐项判断 | 来源级政策矩阵、法务审查、下架/纠错机制和公开分级 |
| 运营与成本 | 中 | 全量静态、分级动态和增量回归可以控制测试成本 | Skill 数量、模型 Token、外部 API、设备和人工复核成本持续增加 | 去重、风险分层、代表性抽样、预算熔断和单位测试成本看板 |
| 商业化 | 中 | 专业用户和企业存在降低选型、测试和治理成本的价值 | 用户是否愿为“证据与推荐”付费仍需验证 | 付费访谈、试点转化、Bundle 采纳率和节省时间测量 |

**综合结论：有条件可行，适合先做 V0 证据链 PoC，不适合一开始承诺三家全量原生自动化。**

继续投入的四个闸门：

1. **来源闸门**：五类首期来源至少形成稳定、可追溯、可增量的发现方式；无法稳定接入的来源允许人工补录，但必须显示覆盖状态；
2. **测试闸门**：50 个代表性 Skill 完成来源、静态检测、沙箱运行、基线和证据页闭环；
3. **合规闸门**：明确每类 Artifact 能否取得、执行、保存和公开结果，三家原生测试未通过审查前不公开排名；
4. **价值闸门**：目标用户能用项目模板或分析流程选出 Bundle，并在盲测或试点中比自行搜索明显节省时间或降低失败率。

任一闸门不通过时，应缩小来源、测试类型或公开范围，而不是用不可验证的“全量”宣传补足能力缺口。

## 5. 产品目标与非目标

### 5.1 产品目标

| 编号 | 目标 |
| --- | --- |
| G-001 | 建立覆盖三家办公 Agent 和主要公开社区的 Skill 发现体系 |
| G-002 | 为每个 Skill 建立来源、版本、内容哈希、许可证、依赖和兼容性档案 |
| G-003 | 对所有可取得 Artifact 的候选 Skill 执行结构、质量、安全、权限和可运行性静态检测 |
| G-004 | 对通过准入的 Skill 执行可复现的标准任务测试 |
| G-005 | 区分 Skill 本体效果、平台兼容性和平台原生端到端效果 |
| G-006 | 支持同类 Skill 横向比较、同一 Skill 纵向版本比较和跨平台交叉比较 |
| G-007 | 根据具体项目输出轻量、平衡、增强三套 Skill Bundle |
| G-008 | 让每个公开评分都能追溯到测试环境、任务、版本、次数和证据 |
| G-009 | 为企业提供内部批准清单、版本锁定、风险策略和使用治理 |

### 5.2 明确非目标

| 编号 | 不做事项 | 原因 |
| --- | --- | --- |
| NG-001 | 获取或评测企业私有 Skill | 无访问权，也不符合产品公开数据边界 |
| NG-002 | 提供 Skill 文件下载 | 增加再分发、版权、版本和供应链责任，不是核心价值 |
| NG-003 | 镜像 WorkBuddy、千问办公或豆包工作市场 | 无必要且存在协议、版权和维护风险 |
| NG-004 | 用单一全局总分定义所有 Skill 优劣 | 不同任务、行业和权限场景不可直接比较 |
| NG-005 | 把 Skill、连接器和专家数量混为一谈 | 三者的作用、依赖、权限和验收方式不同 |
| NG-006 | 在用户不知情时自动安装或运行 Skill | 用户必须掌握安装、授权和高风险操作决定权 |
| NG-007 | 首期处理真实支付、生产删除和不可逆审批 | 风险和责任过高，先通过模拟环境验证 |
| NG-008 | 承诺“所有公开 Skill 都能完成动态测试” | 部分 Skill 缺许可证、依赖、账号、运行环境或安全条件 |

## 6. 名词与分类口径

### 6.1 核心名词

| 名词 | 定义 |
| --- | --- |
| Skill | 面向 Agent 的可复用专业说明、流程、脚本和资源包，通常包含 `SKILL.md` |
| 连接器/MCP | 连接外部账号、数据或工具的能力接口，可能要求 OAuth、密钥或服务端部署 |
| 专家/工作伙伴 | 包含角色、方法、知识、工具配置或多 Skill 编排的上层 Agent 单元 |
| Skill Artifact | 某一来源、某一版本的原始 Skill 文件集合 |
| Candidate | 已发现但尚未完成全部准入的 Skill 候选 |
| Test Run | 固定环境中一次可追溯的 Skill 测试执行 |
| Bundle | 面向某个项目的一组 Skill、依赖、连接器前置条件、权限和验收规则 |
| Neutral Test | 不依赖三家专有运行时的中立沙箱测试 |
| Native Test | 在 WorkBuddy、千问办公或豆包工作实际客户端/服务中完成的测试 |

### 6.2 Skill 与其他能力的边界

| 类型 | 解决的问题 | 是否参与 Skill 排名 |
| --- | --- | --- |
| Skill | 告诉 Agent 何时、按什么步骤、用什么标准完成任务 | 是 |
| 连接器/MCP | 提供外部数据和可执行工具 | 否，单独评分并作为 Skill 依赖 |
| 专家/工作伙伴 | 提供角色、方法和多能力编排 | 否，单独建立专家/套件评测 |
| 提示词模板 | 提供一次性或固定格式提示 | 只有满足可复用 Skill 结构时才纳入 |
| Agent 应用 | 完整交互应用或服务 | 作为相邻对象，不直接按 Skill 规则评分 |

### 6.3 收录状态

每个 Skill 必须有且只有一个当前主状态：

1. `DISCOVERED`：已发现；
2. `METADATA_ONLY`：仅能获取名称和来源；
3. `ACQUIRED`：已通过正常渠道取得测试副本；
4. `STATIC_REVIEWED`：已完成静态检测；
5. `QUARANTINED`：命中安全或许可阻断；
6. `RUNNABLE`：满足动态测试条件；
7. `NEUTRAL_TESTED`：完成中立环境测试；
8. `NATIVE_TESTED`：完成至少一个平台原生测试；
9. `VERIFIED`：达到规定证据等级；
10. `STALE`：版本或测试环境过期；
11. `REMOVED`：原始来源删除、作者撤回或平台停止展示。

## 7. 收录范围与来源策略

### 7.1 收录原则

“我们能拿到的所有公开 Skill”定义为同时满足以下条件的候选：

1. 任何普通用户可见，或由创作者明确公开；
2. 可通过公开页面、官方 API、官方客户端正常安装、公开仓库或作者提交取得；
3. 不需要绕过验证码、权限、企业空间、付费墙、限流或技术保护；
4. 不属于泄露、误公开、盗取、未授权备份或他人私有资源；
5. 来源和作者信息可追溯。

### 7.2 首期来源

| 来源 | 获取内容 | MVP 接入方式 |
| --- | --- | --- |
| WorkBuddy 公开市场 | 名称、描述、来源、公开可安装 Skill | 官方页面/正常客户端流程/经确认的公开包；不镜像市场 |
| 千问办公公开扩展 | 名称、描述、分享链接、公开可安装 Skill | 官方页面、正常客户端和本地已安装目录；无批量接口时保留人工补录 |
| 豆包工作公开 Skill | 名称、描述、公开可安装或自建示例 | 官方页面和正常客户端；发布初期先做格式与路径 PoC |
| GitHub | 包含 `SKILL.md` 或已知 Skill 结构的公开仓库 | GitHub API、代码搜索和仓库元数据 |
| Hugging Face | 包含 Skill 文件、Agent 能力包或相关公开仓库 | Hub API、仓库卡和许可证元数据 |
| 创作者提交 | 作者主动提交的公开 Skill | 网页表单或仓库链接 |

### 7.3 明确排除的来源

- 企业组织空间和企业私有 Skill；
- 个人未公开 Skill；
- 需要借用、购买、共享或批量注册他人账号才能取得的内容；
- 来源不明的网盘包、聊天群泄露包和逆向导出包；
- 已被作者删除但在非授权缓存中留存的内容；
- 绕过平台反爬、加密或权限控制取得的内容。

### 7.4 去重与同源识别

平台必须同时保留“出现次数”和“不同内容数量”，避免把复制文件误认为独立 Skill。

去重层级：

1. 文件 SHA-256 完全相同；
2. Skill 目录归一化哈希相同；
3. 去除格式差异后正文相同；
4. 高语义相似但内容不同；
5. 同名不同来源；
6. 同一上游项目的 Fork 或镜像。

完全重复的 Skill 共享测试结果，但保留全部来源关系；内容发生变化后必须生成新的 Artifact Version。

## 8. 目标用户与核心需求

### 8.1 个人专业用户

典型角色：运营、产品经理、研究员、销售、设计师、开发者、财务、人力资源人员。

### 8.3 企业 AI 管理员

- 建立企业批准使用的公开 Skill 清单；

- 观察使用效果和升级影响。

### 8.4 Skill 创作者

核心需求：

- 证明 Skill 的真实能力；
- 获得兼容认证和安全检查；

### 8.5 评测与运营人员

核心需求：

- 维护测试集和评分规则；
- 审查异常排名和申诉；
- 控制公开证据和受限证据；
- 处理恶意 Skill、安全事件和下架。

## 9. 典型用户旅程

### 9.1 按任务找 Skill

1. 用户输入“整理 30 份访谈并生成可编辑 PPT”；
2. 平台识别任务、产物、数据类型和风险；
3. 用户选择 WorkBuddy、千问办公、豆包工作或“尚未确定”；
4. 系统过滤不兼容、缺少依赖和高风险 Skill；
5. 展示候选 Skill 的效果、稳定性、权限、成本和证据等级；
6. 用户查看对比页；
7. 用户跳转到原始来源安装。

### 9.2 生成项目 Skill Bundle

1. 用户创建项目；
2. 通过模板或智能体问答补充项目目标；
3. 系统拆解任务和交付物；
4. 召回候选 Skill；
5. 解析依赖、冲突、权限和总成本；
6. 输出轻量、平衡、增强三套方案；
7. 用户选择、替换或排除 Skill；
8. 系统生成项目清单、安装来源、版本锁和验收用例；
9. 用户决定是否前往原平台安装。

### 9.3 比较同类 Skill

1. 用户勾选 2～5 个 Skill；
2. 对比相同测试任务下的通过率和结果；
3. 查看不同平台、模型和版本的表现；
4. 查看依赖、权限、成本和失败案例；
5. 根据项目权重重新计算适配排序。

### 9.4 创作者提交测试

1. 创作者提交公开仓库链接和版本；
2. 系统验证所有权、许可证和来源；
3. 执行静态检测；
4. 通过后进入动态测试队列；
5. 创作者查看报告；
6. 结果公开前提供纠错和申诉入口，但不得干预测试标准。

## 11. Skill 发现与采集模块

### 11.1 发现规则

系统应支持：

- 文件名和目录结构发现；
- 公开市场分类和搜索结果发现；
- 已知 Skill 仓库递归发现；
- 作者、组织和项目关联发现；
- Fork、镜像和上游来源追踪；
- 增量更新和删除检测。

### 11.2 采集字段

每条来源记录至少包含：

- 来源平台；
- 原始 URL；
- 来源对象 ID；
- 作者或发布组织；
- Skill 名称和原始描述；
- 仓库、分支、Commit 或平台版本；
- 首次发现和最后同步时间；
- 可见性；
- 许可证及识别置信度；
- 原始内容哈希；
- 是否允许内部测试；
- 是否允许公开展示衍生结果；
- 是否允许内部留存测试副本；
- 下架或撤回状态。

### 11.3 临时测试副本策略

- 平台只对动态测试需要的 Artifact 创建内部临时副本；
- 临时副本与公共展示存储分离；
- 许可证允许归档时，可保存不可公开下载的版本副本以支持复现；
- 许可证不清或仅允许有限使用时，测试结束后删除文件，只保留哈希、来源、环境和结果；
- 不在网页或 API 返回原始文件正文。

## 12. 全量静态检测

### 12.1 检测目标

静态检测面向所有能够取得内容的候选 Skill，是全量覆盖的主要手段。

### 12.2 检测维度

#### A. 结构与规范

- 是否包含 `SKILL.md`；
- YAML Frontmatter 是否有效；
- 名称、描述、触发条件是否存在；
- 目录引用是否有效；
- 脚本、资源和参考文件是否缺失；
- 是否存在绝对路径、作者本机路径或不可移植路径；
- 是否包含未完成占位符、TODO 或示例密钥。

#### B. 路由与触发

- 描述是否清楚说明何时使用；
- 是否存在过宽触发导致误调用；
- 是否与常见 Skill 名称冲突；
- 是否包含正向和负向边界；
- 是否依赖只能由特定模型理解的隐式规则。

#### C. 依赖

- 操作系统；
- 命令行程序；
- Python、Node 或其他运行时；
- 包管理器和版本；
- 外部 API；
- OAuth、账号、密钥和环境变量；
- MCP 或连接器；
- 付费服务；
- 本地应用和浏览器登录态。

#### D. 权限与数据流

- 文件读取、写入、删除；
- Shell 或脚本执行；
- 网络访问；
- 浏览器控制；
- 邮件、消息和内容发布；
- 支付、交易、审批；
- 摄像头、麦克风、屏幕；
- 个人信息、企业数据或凭证处理；
- 数据发往哪些第三方。

#### E. 安全

- 提示词注入和指令层级破坏；
- 凭证读取、打印、上传或硬编码；
- 隐藏网络请求和数据外传；
- 下载后执行；
- 混淆代码；
- 危险命令和无范围删除；
- 持久化、后门和自启动；
- 供应链依赖风险；
- 绕过访问控制和反爬措施；
- 社会工程或欺骗性授权。

#### F. 许可与来源

- 是否存在许可证；
- 许可证是否覆盖 Skill 内容和附带脚本；
- 作者是否与来源一致；
- 是否复制其他 Skill 且未保留声明；
- 是否存在商业使用、修改、测试或展示限制；
- 是否需要人工复核。

### 12.3 静态检测输出

输出必须区分：

- 通过；
- 警告；
- 阻断；
- 无法判断；
- 需要作者补充；
- 需要人工复核。

安全阻断不能被普通质量分抵消。

## 13. 动态测试系统

### 13.1 准入条件

候选 Skill 同时满足以下条件才进入动态测试：

1. 来源可追溯；
2. 内部测试权利已确认或获得授权；
3. 未命中高危安全阻断；
4. 依赖可安装或可安全模拟；
5. 存在适配的标准任务；
6. 可在隔离环境运行；
7. 测试费用和外部调用受到限制。

### 13.2 测试层级

#### L0：格式解析

验证是否能被目标解析器正确发现和加载。

#### L1：触发测试

- 正向样本：应该触发时是否触发；
- 负向样本：不应该触发时是否误触发；
- 改写样本：不同表达下是否稳定；
- 多 Skill 环境：是否与其他 Skill 冲突。

#### L2：中立任务测试

在统一模型、工具、文件和网络策略下，对 Skill 本体产生的增益进行测试。

#### L3：故障与安全测试

- 缺少输入；
- 依赖不可用；
- 网络超时；
- 权限不足；
- 恶意文档和网页提示注入；
- 重复执行；
- 用户中途取消；
- 高风险操作拒绝或人工确认。

#### L4：平台原生测试

在 WorkBuddy、千问办公或豆包工作实际环境中测试安装、触发、执行、产物和权限。

#### L5：组合测试

测试多个 Skill 同时启用后的覆盖、冲突、上下文占用和整体项目完成率。

### 13.3 测试基线

动态测试必须包含：

- 无 Skill 基线；
- 目标 Skill；
- 必要时加入同类候选；
- 必要时加入不相关 Skill 作为误触发控制；
- 固定模型、宿主、工具、输入和运行配置。

### 13.4 重复次数

- 冒烟测试：至少 1 次；
- 初步评分：每个任务至少 3 次；
- 验证评分：每个任务至少 5 次；
- 高波动或高风险任务：至少 10 次或采用序贯停止规则。

### 13.5 外部服务测试

- 默认使用 Mock、沙箱或测试租户；
- 不使用个人真实邮箱、通讯录、生产数据库和支付账户；
- 必须设置调用次数和费用上限；
- 真实账号测试必须获得账号所有者明确授权；
- 发送、发布、删除、支付和审批默认不执行真实副作用。

## 14. 标准任务体系

### 14.1 首期任务类别

| 类别 | 典型任务 | 主要验收方式 |
| --- | --- | --- |
| 调研 | 多来源检索、事实核查、竞品报告 | 引用有效性、覆盖率、事实一致性、结构 |
| 文档 | Word 报告、合同整理、会议纪要 | 必要章节、格式、可编辑性、内容准确性 |
| 表格 | 清洗、公式、透视、图表、分析 | 公式校验、数据一致性、错误单元格、结果值 |
| 演示 | PPT 大纲、排版、可编辑幻灯片 | 页数、结构、可读性、元素可编辑、渲染检查 |
| 网页 | 信息页、看板、交互页面 | 构建、浏览器运行、响应式、可访问性、功能测试 |
| 文件处理 | 分类、重命名、转换、批处理 | 文件快照 Diff、无越界修改、幂等性 |
| 开发 | 代码修改、测试、审查、部署准备 | 自动测试、静态检查、Diff、回归 |
| 内容运营 | 文案、选题、渠道适配 | 约束满足、事实、风格、平台规则 |

### 14.2 测试任务结构

每个测试任务必须包含：

- 任务 ID 和版本；
- 适用类别和难度；
- 输入文件或数据生成方式；
- 用户指令；
- 允许工具和权限；
- 时间和成本上限；
- 确定性校验器；
- 人工或 LLM 辅助评审规则；
- 失败条件；
- 数据和答案泄露防护；
- 是否可公开测试证据。

### 14.3 防止测试污染

- 公开示例不能与正式测试完全相同；
- 测试数据应参数化和周期轮换；
- 创作者不能看到全部隐藏测试；
- 排名异常提升时触发新样本复测；
- 训练集式硬编码只能通过公开示例，不得命中隐藏数据。

## 15. 评分与排名体系

### 15.1 基本原则

1. 安全采用准入门槛，不被总分抵消；
2. 任务效果必须相对无 Skill 基线计算；
3. 不同类别不使用同一全局排序；
4. 平台、模型、版本和时间必须可见；
5. 没有动态测试就不显示动态能力分；
6. 一次运行不产生“已验证”标签；
7. LLM 裁判只作为补充，不作为唯一证据；
8. 公开分数必须同时显示证据等级和样本量。

### 15.2 核心指标

#### 任务成功率

`Pass Rate = 通过次数 / 总运行次数`

#### Skill 增益

`Uplift = 使用 Skill 的通过率 - 无 Skill 基线通过率`

#### 触发准确率

分别计算触发 Precision、Recall、误触发率和漏触发率。

#### 稳定性

综合成功率方差、重复执行一致性、故障恢复和幂等性。

#### 成本效率

综合 Token、平台积分、外部 API 费用、运行时间和人工介入次数。

### 15.3 多维评分卡

| 维度 | 默认权重 | 说明 |
| --- | ---: | --- |
| 任务效果 | 35% | 通过率、基线增益和输出质量 |
| 稳定性 | 15% | 重复运行、恢复和方差 |
| 触发质量 | 10% | 正确触发且避免误触发 |
| 权限与隐私 | 10% | 最小权限、数据流透明度 |
| 成本效率 | 10% | 时间、Token、积分和外部费用 |
| 平台兼容性 | 10% | 宿主、模型、系统和工具适配 |
| 可维护性 | 5% | 版本、依赖、更新和作者维护 |
| 文档与可解释性 | 5% | 输入、步骤、输出和失败边界 |

以上权重仅为默认场景。项目推荐必须根据用户目标动态调整，不能把默认综合分当成所有场景的绝对排名。

### 15.4 证据等级

| 等级 | 条件 |
| --- | --- |
| A | 当前版本；至少 3 个代表性任务；每项至少 5 次；含基线；主要结论可确定性验证 |
| B | 至少 2 个任务；每项至少 3 次；含基线；环境记录完整 |
| C | 仅冒烟或单任务测试；结果可参考但不足以稳定排名 |
| D | 仅静态检测或兼容性推断，不得展示动态效果结论 |
| U | 尚未验证 |

### 15.5 排名类别

- 按具体任务排名；
- 按职业和项目类型排名；
- 按平台排名；
- 按安全和最小权限排名；
- 按成本效率排名；
- 按证据等级排名；
- 新发布 Skill 榜；
- 被低估 Skill 榜；
- 版本进步榜。

不设置脱离任务和证据等级的“全站最好 Skill”。

## 16. 横向、纵向与交叉比较

### 16.1 横向比较

固定：

- 同一任务；
- 同一输入；
- 同一宿主；
- 同一模型；
- 同一工具和权限；
- 同一时间窗口。

比较不同 Skill 的任务效果、成本、稳定性和权限。

### 16.2 纵向比较

比较同一个 Skill：

- 不同版本；
- 不同模型；
- 不同客户端版本；
- 不同时间；
- 修复前后；
- 单独启用和加入 Bundle 后。

### 16.3 交叉比较

交叉矩阵为：

`Skill × 宿主 × 模型 × 工具 × 操作系统 × 数据复杂度 × 权限`

当平台内置模型、工具和上下文无法统一时，结果必须标记为“平台端到端表现”，不能把全部差异归因于 Skill。

## 17. 跨平台兼容体系

### 17.1 Portable Core

平台抽取可移植核心：

- `name`；
- `description`；
- 主体说明；
- `scripts/`；
- `references/`；
- `assets/`；
- 输入输出约定；
- 依赖和权限声明。

### 17.2 Host Overlay

宿主专属内容单独记录：

- 目录位置；
- Frontmatter 扩展字段；
- `allowed-tools`；
- Hooks；
- 子 Agent；
- UI 组件；
- 平台内置连接器 ID；
- 专有变量和运行时；
- 平台专属审批和权限。

### 17.3 兼容状态

| 状态 | 含义 |
| --- | --- |
| Native | 原始来源即面向目标平台，已完成原生测试 |
| Compatible | 无修改或仅修改安装位置即可使用 |
| Adaptable | 需要字段、路径或依赖适配 |
| Partial | 只能运行部分能力 |
| Blocked | 依赖缺失、安全、许可或平台限制阻断 |
| Unsupported | 技术上不支持 |
| Unverified | 尚未完成验证 |

平台不能仅凭文件结构相似就标记“兼容”，至少需要加载或冒烟测试证据。

## 18. 项目模板与智能体个性化分析

### 18.1 两种入口

#### 模板入口

用户选择预设项目模板，例如：

- 竞品调研和汇报；
- 电商运营周报；
- 新产品发布；
- 招聘和入职；

- 内容矩阵生产；
- 网站开发；
- 软件研发；
- 企业知识整理。

#### 智能体分析入口

用户用自然语言描述项目，推荐智能体逐步提取结构化信息。已经确认的信息不得重复询问。

### 18.2 项目画像字段

- 项目名称和类型；
- 当前阶段；
- 业务目标；
- 具体任务；
- 输入数据和格式；
- 需要交付的产物；
- 目标平台；
- 操作系统和设备；
- 可使用的连接器、账号和软件；
- 数据敏感等级；
- 是否允许联网、脚本和文件写入；
- 预算、积分、时间要求；
- 团队规模和技术水平；
- 必须人工确认的操作；
- 已安装 Skill；
- 用户明确排除的 Skill 或来源。

### 18.3 推荐流程

1. 项目任务拆解；
2. 硬性条件过滤；
3. 语义和分类召回；
4. 平台兼容过滤；
5. 权限和安全过滤；
6. 依赖补全；
7. 重复和冲突消除；
8. 动态权重排序；
9. Bundle 组合优化；
10. 输出解释、证据和替代方案。

### 18.4 Bundle 输出

每个 Bundle 包含：

- 项目适用范围；
- Skill 名称、来源、版本和哈希；
- 每个 Skill 承担的任务；
- 依赖的连接器和外部服务；
- 所需权限；
- 安装顺序和原始来源链接；
- 预计成本和执行时间；
- 已知冲突和限制；
- 验收测试；
- 失败回退；
- 可替换候选；
- 不推荐或排除项及原因。

### 18.5 三档方案

| 方案 | 定位 |
| --- | --- |
| 轻量 | Skill 数量最少、依赖最少、权限最低、适合快速开始 |
| 平衡 | 效果、成本、稳定性和权限综合最优，默认推荐 |
| 增强 | 覆盖更多复杂任务，但依赖、费用和维护成本更高 |

### 18.6 冲突检测

至少检测：

- 触发描述重叠；
- 同名 Skill；
- 同一任务重复覆盖；
- 工具或命令冲突；
- 环境变量冲突；
- 运行时和包版本冲突；
- 过度占用上下文；
- 权限叠加超出项目允许范围；
- 一个 Skill 的输出不符合下一个 Skill 的输入；
- 高风险副作用链路。

## 24. 安全、隐私与合规要求

### 24.1 基本原则

- 只收录公开且正常可得的 Skill；
- 企业私有 Skill 不进入采集、存储或测试；
- 公共网站只展示名称、来源、结论和必要证据，不分发文件；
- 不绕过平台权限、验证码、反爬、限流和付费机制；
- 测试和公开结果分别做权限判断；
- 所有密钥使用短期注入和最小权限；
- 高风险操作必须人工确认。

### 24.2 平台结果公开分级

| 结果类型 | 默认公开策略 |
| --- | --- |
| 公开元数据和来源 | 可公开，保留来源说明 |
| 中立沙箱静态与动态结果 | 经许可和事实复核后公开 |
| 三家平台兼容性冒烟结果 | 经协议和法务评估后公开 |
| 三家平台原生基准和排名 | 获得授权或明确法律审查结论后公开；否则仅内部/私有报告 |
| 企业私有 Skill | 当前产品不接收、不测试、不展示 |

### 24.3 商标和中立性

- 可以使用平台名称说明兼容性和来源，但不得暗示官方合作；
- 未获授权不得使用官方认证、官方推荐等表述；
- 页面应显示“独立评测，与相关平台无隶属关系”；
- 排名和评价提供方法、日期、纠错和申诉入口。

### 24.4 供应链安全

- 生成 SBOM 或依赖清单；
- 固定依赖版本；
- 扫描恶意包和已知漏洞；
- 阻止测试环境访问宿主密钥和其他任务数据；
- Artifact 使用哈希校验；
- 原始文件、标准化结果和测试产物分区存储；
- 安全事件可快速撤回公开推荐和所有受影响 Bundle。

## 25. 非功能需求

### 25.1 可追溯性

每个公开结论必须可追溯到：

- 原始来源；
- Artifact 版本和哈希；
- 测试任务版本；
- 测试环境；
- 执行次数；
- 校验结果；
- 评分规则版本；
- 发布时间。

### 25.2 可复现性

- 测试环境镜像版本化；
- 输入数据和校验器版本化；
- 模型和宿主无法固定时明确标注；
- 外部服务不可复现时降低证据等级；
- 允许授权人员重新运行同一测试。

### 25.3 性能

- 普通搜索首屏 P95 小于 2 秒；
- 详情页 P95 小于 2.5 秒；
- 推荐初步结果 P95 小于 15 秒；
- 长时项目分析应显示阶段、预计时间和取消入口；
- 静态扫描支持水平扩展和增量处理。

### 25.4 可用性

- 公共搜索和详情服务月可用性目标 99.9%；
- 测试队列故障不应影响已发布结果查询；
- 评分和推荐服务失败时不得回退为无证据推荐；
- 所有长任务支持取消、重试和状态查看。

### 25.5 可访问性和国际化

- 首期中文；
- Skill 原始名称和原始语言保留；
- 中文说明是平台生成内容，必须与原文分开；
- Web 端达到 WCAG 2.1 AA 的主要交互要求；
- 评分不能只靠颜色表达。

### 28.2 V1A：公开目录与中立评测 MVP（6～10 周）

## 29. MVP 验收标准

### 29.1 来源与数据

- GitHub 和 Hugging Face 接入可自动增量发现；
- WorkBuddy、千问办公、豆包工作分别完成公开来源适配 PoC；
- 每条 Skill 均有来源 URL、作者/组织、发现时间和状态；
- 可取得内容的 Artifact 均生成 SHA-256；
- 完全重复内容可以合并并保留来源关系；
- 采集与上传入口不能接收企业私有 Skill，公开库中不得出现企业私有内容。

### 29.2 静态检测

- 90% 以上可取得 Artifact 在规定时间内完成静态检测；
- 高危命令、凭证外传、隐藏网络请求和越权行为可触发阻断；
- 许可证不明内容标记清楚；
- 静态检测失败不会生成动态能力分。

### 29.3 动态测试

- 至少覆盖调研、文档、表格、演示、网页五类任务；
- 至少 100 个去重且可运行 Skill 完成中立动态测试；
- 每个已验证 Skill 至少有基线和 3 次重复运行；
- 运行环境、模型、任务、成本和证据完整保存；
- 测试环境间不存在文件、密钥和会话串扰。

### 29.4 产品体验

- 用户能通过任务搜索找到候选 Skill；
- 用户能比较 2～5 个 Skill；
- 未动态测试的 Skill 明确显示“未实测”；
- 用户可以完成一次项目画像；
- 系统能输出轻量、平衡、增强三套 Bundle；
- Bundle 能说明每项 Skill 的职责、依赖、权限、限制和替代项；
- 所有安装动作跳转原始来源；
- 产品不存在 Skill 文件下载入口。

### 29.5 安全与治理

- 公开页面不泄露原始 Skill 正文、脚本和测试凭证；
- 高风险 Skill 进入隔离或阻断状态；
- 评分可以撤回并保留审计记录；
- 创作者可以提交纠错和申诉；
- 私有租户数据不会出现在公共搜索、推荐或统计中。

## 30. 主要风险与缓解措施

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 三家平台缺少公开批量接口 | 无法保证自动全量同步 | 官方合作、公开页面、正常客户端、人工补录和来源覆盖率声明 |
| 平台协议限制公开原生评测 | 无法公开三家端到端榜单 | 中立测试优先；原生结果分级；商务授权和法务审查 |
| Skill 数量巨大且重复严重 | 动态测试成本失控 | 哈希和语义去重；全量静态；动态分层和增量回归 |
| 测试结果受模型和平台变化影响 | 排名快速过期 | 绑定环境和日期；过期标记；版本变化触发回归 |
| LLM 裁判偏差 | 评分不可信 | 确定性验证优先；双盲；多评审；公开方法和申诉 |
| 恶意 Skill 攻击测试环境 | 数据泄露或供应链事故 | 强沙箱、无生产凭证、网络白名单、一次性环境、人工阻断 |
| 创作者刷榜或针对测试集优化 | 榜单失真 | 隐藏任务、参数化数据、异常检测、证据等级和周期轮换 |
| 名称、来源或评价争议 | 品牌和法律风险 | 清晰来源、中立声明、事实复核、纠错和下架机制 |
| 推荐 Bundle 权限叠加 | 风险超过单个 Skill | 组合级权限视图、风险门槛、人工确认和最小权限方案 |
| 用户只看总分 | 误选 Skill | 默认展示适用场景、多维评分、证据和限制，不提供脱离任务的全局榜 |

## 31. 已排除、保留和延期方案

### 31.1 已排除

| 方案 | 结论 | 排除原因 |
| --- | --- | --- |
| 三家市场完整镜像 | 排除 | 与推荐目标无关，增加版权、协议和同步责任 |
| 在本站提供 Skill 压缩包下载 | 排除 | 平台不销售 Skill，用户应回原始来源安装 |
| 获取或评测企业私有 Skill | 排除 | 用户已明确当前不做；无访问权，且超出公开 Skill 平台的数据边界 |
| 只按下载量或 Star 排名 | 排除 | 只代表热度，不代表效果、安全和适配 |
| 用一次 LLM 阅读结果直接打分 | 排除 | 不稳定、不可复现、容易被提示词操纵 |
| 所有 Skill 一个总榜 | 排除 | 不同任务、权限、成本和平台无法公平比较 |
| 推荐后自动静默安装 | 排除 | 用户失去安装和授权控制权 |

### 31.2 保留但不作为主路径

| 方案 | 保留方式 |
| --- | --- |
| 热度榜 | 作为发现信号，明确标记“热度”，不等于质量 |
| 用户评分 | 作为体验反馈，采用防刷和贝叶斯校正，不替代测试 |
| LLM 评审 | 用于风格和复杂产物辅助评审，不作为唯一裁判 |
| 手工收录 | 在平台无 API 或刚发布时作为补充，保留操作记录 |
| 用户本地测试 Agent | 未来用于用户授权的真实环境验证，默认结果私有 |

### 31.3 延期

| 方案 | 延期原因 | 进入条件 |
| --- | --- | --- |
| 付费 Skill 市场 | 涉及交易、退款、版权和售后 | 供给质量、法务和支付体系成熟后单独立项 |
| 一键跨平台安装 | 三家安装协议和目录仍在变化 | 获得官方协议、深链接或稳定适配方式 |
| 全平台公开原生排行榜 | 协议和评测授权未完成 | 商务授权和法律审查通过 |
| 高风险业务自动执行 | 责任和数据风险高 | 沙箱、审批、保险和专业合规成熟 |
| 更多国内外来源 | 首期需要集中验证三家主平台 | MVP 数据和测试闭环稳定后扩展 |
| 企业授权的私有 Skill 评测 | 当前产品明确排除，且需要完全不同的数据责任 | 只有新的企业需求、主动授权、隔离与法务方案均成立后另行立项；不自动进入现路线图 |

## 34. 最终产品原则

1. 收录范围尽可能广，但访问手段必须正常、公开、可审计；
2. 所有能取得的公开 Skill 做静态检测，动态测试必须通过准入；
3. 当前产品不获取、不测试、不展示企业私有 Skill；
4. 公开页面只展示名称、来源、评分、证据、兼容性和推荐，不提供 Skill 文件；
5. 用户回原始来源安装，平台不替代原作者和原市场；
6. 真实效果由任务、基线、重复运行和证据证明；
7. 安全是门槛，不能被高效果分抵消；
8. 推荐的是完成项目所需的能力组合，不鼓励无目的安装；
9. 任何高风险操作都保留用户确认、取消和接管权；
10. 所有结论都允许复核、纠错、申诉和随版本变化更新。
